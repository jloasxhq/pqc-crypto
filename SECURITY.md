# Security policy

## Validation status

`@quxtech/pqc-crypto` is **not FIPS 140-3 validated**. Version 2.x is
"FIPS-aligned" — it follows NIST published algorithm specifications
(FIPS 203 ML-KEM, FIPS 204 ML-DSA, FIPS 202 SHA-3, SP 800-132 PBKDF2)
and ships opt-in self-tests via `setFipsMode(true)`, but the underlying
implementations come from `@noble/*` pure-JS packages and are not the
subject of a NIST CMVP module validation.

A future `PqcProvider` abstraction (planned for v3.x) will allow
delegating approved-mode operations to a validated cryptographic
backend (OpenSSL FIPS 3.x, BoringCrypto, PKCS#11 HSM).

## Reporting a vulnerability

Email **security@quxtech.com** with the subject `pqc-crypto: <short
summary>`. Please include:

- Affected version(s)
- Reproduction steps
- Suspected impact
- Whether you intend to disclose publicly

We aim to acknowledge within 2 business days and triage within 5
business days. Coordinated disclosure preferred; please give us 90
days from acknowledgement before public disclosure unless an active
exploit demands otherwise.

## Out of scope

- Side-channel attacks against the host CPU executing pure-JS code
  (timing, cache, EM): pure-JS PQC inherits @noble's defenses but
  cannot guarantee constant-time execution on all V8 builds. If side-
  channel resistance is required, use a hardware HSM via the future
  PKCS#11 provider.
- Bugs in `@noble/post-quantum`, `@noble/hashes`, or `@noble/ciphers`:
  please report to those projects directly. We will issue a coordinated
  patch once upstream is fixed.
- Application-layer misuse (weak passphrases for `serializeKeys`, key
  reuse, IV reuse, etc.): documented in the README's "Memory hygiene"
  section; we cannot enforce caller-side practices.

## Supply chain

Releases are published via the QUX private Verdaccio registry at
`https://npm.qux.tv:4873/`. The registry's TLS certificate is a publicly-
trusted Let's Encrypt certificate for the `npm.qux.tv` host. Source for
v2.x is mirrored in the QUX Gitea instance under `quxadmin/pqc-crypto`.

A signed SBOM is on the v2.x roadmap (CycloneDX format); not yet
shipped with the package as of 2.0.0.

## Cryptographic Erasure / Key Rotation

Production keys generated by 1.x and 2.x trace back to OS CSPRNG
(`crypto.randomBytes` on Node, ultimately delegating to OpenSSL). There
is no known weak-RNG path requiring forced rotation when upgrading
between minor versions.

When upgrading from v1.x to v2.x:

- Any existing `server-keys.enc` files written by v1 (HKDF envelope)
  remain readable by v2's `deserializeKeys`. No re-key required.
- New saves automatically use the v2 PBKDF2 envelope. To force
  re-encryption to v2 immediately, call `serializeKeys` and overwrite
  the file.
- Once on v2, downgrading to v1 will lose access to any v2-format
  envelopes. Keep a v1 backup if you may need to roll back.
